Durata target: 25 minuti. Formato: 20 slide, circa 75 secondi per slide. Pubblico: tecnico, ma non necessariamente esperto di MCP o AI distribution. Obiettivo narrativo: un percorso guidato — dalla definizione di MCP, alla piattaforma PagoPA, ai dettagli tecnici, all'estensione VS Code.

Speaker note (0:45): Aprire con il messaggio principale: non presentiamo un singolo tool, ma un'infrastruttura che porta asset AI versionati, governati e aggiornabili direttamente nei workspace dei team. Il percorso parte dalla definizione di MCP per arrivare all'estensione VS Code.

Speaker note (1:00): Siamo qui per capire come funziona il sistema, perché è stato costruito così e come possiamo usarlo. Ogni sezione si appoggia sulla precedente: se capiamo MCP, capiremo perché il server è fatto in quel modo. L'architettura interna del server e i tool avanzati (install, ephemeral, check_updates) sono nell'appendice EXTRA.

Speaker note (0:10): Separatore per la parte definitoria.

Speaker note (1:30): Enfatizzare l'analogia con REST: prima di REST ognuno inventava il proprio protocollo HTTP. MCP fa la stessa cosa per i modelli AI. La protocol version che vedremo nel codice è 2024-11-05 — è la versione che il server dichiara nell'handshake initialize.

Speaker note (1:30): Mostrare il flusso come conversazione. Il punto chiave è che il modello riceve lo schema dei tool in fase di discovery e poi usa quello schema per costruire le chiamate. Non c'è hardcoding lato modello.

Speaker note (0:10): Separatore per passare alla piattaforma.

Speaker note (1:20): Il punto architetturale cruciale: il server è "modelless". Non chiama provider AI, non esegue skill, non interpreta prompt. Distribuisce descrittori e contenuto Markdown che il modello locale del client usa. Questo è il contrario di un'AI-as-a-service.

Speaker note (1:15): I due moduli sono indipendenti: il server può esistere senza l'estensione e viceversa. L'estensione è il client "umano", il modello AI è il client "automatico". Entrambi parlano con lo stesso server.

Speaker note (1:20): Mostrare che i kind non sono arbitrari — ognuno ha semantica precisa per il modello che lo riceve. Un'instruction con applyTo viene caricata selettivamente per i file che matchano il pattern. Una skill viene letta per esteso prima di eseguire un task.

Speaker note (1:10): Questo manifest è la fonte di verità. Il server lo legge all'avvio e lo indicizza per id. Quando il modello chiede install_asset, il server costruisce il piano a partire da qui: target_path, content del body_file, e dipendenze transitive.

Speaker note (0:10): Separatore per la parte tecnica del server.

Speaker note (1:20): L'API REST è pensata per la navigazione umana e per il mcp-notifier. Il POST /v1/mcp è pensato per i modelli AI. La separazione è netta: il REST plane risponde con JSON strutturato; l'MCP endpoint risponde con JSON-RPC standard.

Speaker note (1:20): Il dispatcher non conosce i tool a priori: li carica da definitions/ tramite ToolDefinitionLoader. Aggiungere un tool significa aggiungere un file JSON in definitions/ e un handler in TOOL_HANDLERS. Non si tocca il dispatcher.

Speaker note (1:20): Sottolineare il contratto: il modello vede solo la definizione JSON. L'handler è codice Python puro, testabile in isolamento. Il dispatcher è ignaro di entrambi finché non li carica all'avvio. Questa separazione permette di aggiungere tool senza toccare il core del protocollo.

Speaker note (1:15): Evidenziare che search_assets è pensato per la fase di scoperta: il modello non conosce a priori cosa c'è nel catalogo, lo chiede. Il risultato è volutamente un summary per non appesantire il contesto.

Speaker note (1:00): Il digest SHA-256 è la parte più importante: permette di rilevare modifiche manuali al file installato. Se qualcuno edita l'asset direttamente nel workspace, il digest non corrisponde più e mcp-notifier segnala il file come "modificato localmente".

Speaker note (1:10): Questo file è il punto di ingresso per tutto: sia per il modello AI (che lo usa per scoprire i tool), sia per mcp-notifier (che lo legge per sapere dove connettersi). Senza questo file, né l'estensione né il modello sanno che il server esiste.

Speaker note (1:30): Questo flusso è il nucleo della presentazione. Il server non fa nulla di "intelligente": risponde a domande. L'intelligenza è nel modello che orchestra le chiamate. Il fatto che il server sia stupido è un pregio architetturale: è testabile, riproducibile, indipendente dal modello.

Speaker note (1:20): Sottolineare la semplicità voluta: non c'è UI, non c'è database, non c'è API di scrittura. Il catalog è il filesystem. Questo significa che il versioning degli asset è il versioning del repository — Git è il sistema di controllo della piattaforma.

Speaker note (0:10): Separatore per la parte dell'estensione.

Speaker note (1:30): L'estensione è il "colla" tra il server e il developer: rende visibile ciò che altrimenti sarebbe invisibile (la versione degli asset installati). Il SSE è fondamentale: evita il polling e permette aggiornamenti istantanei quando il team pubblica una nuova versione di un asset.

Speaker note (1:00): Chiudere con il messaggio pratico: il sistema è già operativo e usabile. Il passo successivo più importante è popolare il catalogo con gli asset reali dei team — la piattaforma è pronta, ora serve il contenuto.

Speaker note (0:10): Appendice tecnica con dettagli sull'architettura interna e sui tool avanzati.

Speaker note (1:20): Il catalog è immutabile a runtime. Aggiungere un nuovo asset significa committare un manifest e riavviare il server (o ricostruire l'immagine Docker). Non ci sono database, non ci sono scritture concorrenti.

Speaker note (1:30): La distinzione install vs ephemeral è fondamentale: install è per asset che devono restare nel repo (e essere aggiornabili), ephemeral è per contesti temporanei. Il fatto che il server restituisca un piano e sia il client a scrivere i file è deliberato: mantiene la piattaforma "modelless".

Speaker note (1:15): Il notifier scansiona i Markdown del workspace cercando frontmatter con source_id e source_version, poi chiama check_updates con quell'array. Se ci sono outdated, mostra la notifica nell'editor.

Speaker note (1:10): install_assets è utile quando si vuole configurare un workspace da zero con un set predefinito di asset (es. tutti gli agent QA). Deduplicare le dipendenze lato server evita scritture duplicate da parte del client.

Speaker note (1:10): ephemeral_load_assets è il tool ideale per "arricchire il contesto al volo". A differenza di install_assets, non lascia traccia nel workspace: tutto rimane nella sessione del modello. Utile per task esplorativi o one-shot che non richiedono persistenza.

Speaker note (1:20): Il versionamento automatico evita il problema del "chi aggiorna il numero di versione nel manifest" — è il workflow che lo fa, deterministicamente, da Git.

Speaker note (1:00): Il comando Initialize Workspace MCP Config è il punto di partenza per nuovi workspace: crea il mcp.json con la URL di default del catalogo PagoPA.
